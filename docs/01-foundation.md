# 01. 토대 (사용자·조직·권한·인증·결재키)

모든 모듈이 의존하는 기준 데이터와 인증·권한 체계. 모듈 코드: **FND**

---

## 1. 임직원·조직 데이터

### FND-001 임직원 관리
시스템 관리자가 임직원을 등록·수정·비활성화한다. 단, **최초 시스템관리자 1명은 시드 마이그레이션으로 생성**한다(등록 권한의 닭-달걀 문제 해소). 초기 비밀번호는 환경변수로 주입하며 최초 로그인 시 변경을 강제한다(상세 `12-dev-environment.md`).
- 임직원 속성: 사번(고유), 이름, ID(로그인용, 고유), 비밀번호(해시 저장), 소속 부서(1개), 직급, 이메일, 연락처, 상태(활성/비활성).
- **AC1**: 사번과 로그인 ID는 중복 등록 시 거부된다.
- **AC2**: 임직원은 반드시 하나의 부서에 소속된다(소속 없음 불가).
- **AC3**: 비활성 임직원은 로그인할 수 없고, 신규 결재선·담당자 지정 대상에서 제외된다.
- **AC4**: 임직원은 물리 삭제할 수 없다(비활성화만 가능).
- **AC5**: 최초 시스템관리자는 시드로 생성되며, 최초 로그인 시 비밀번호 변경이 강제된다.

### FND-002 조직(부서) 관리
- 조직 구조는 **2~3단계 고정 트리**(예: 본부 › 부서, 또는 본부 › 팀 › 파트).
- 부서 속성: 부서코드(고유), 부서명, 상위 부서(루트는 null), 단계(level), 상태(활성/비활성).
- **AC1**: 부서는 최대 3단계까지만 생성 가능하다(4단계 생성 시 거부).
- **AC2**: 부서는 물리 삭제 불가(비활성화만). 비활성화 규칙은 `08-lifecycle-rules.md` LIFE-B 참조.
- **AC3**: 임직원은 동시에 하나의 부서에만 속한다(다중 소속 불가).

## 2. 인증 (로그인)

### FND-003 로그인 (ID + 비밀번호)
- 로그인은 ID + 비밀번호 방식. 인증 성공 시 **Access 토큰(JWT, 짧은 수명) + Refresh 토큰**을 발급한다. Access 만료 시 Refresh로 갱신한다.
- 비밀번호는 단방향 해시(예: BCrypt)로 저장한다. 평문 저장 금지.
- **AC1**: 올바른 ID/비밀번호로 로그인하면 유효한 Access·Refresh 토큰이 발급된다.
- **AC2**: 비활성 계정은 올바른 비밀번호여도 로그인이 거부된다.
- **AC3**: 비밀번호는 8자 이상, 영문+숫자를 포함해야 한다(미충족 시 설정 거부).
- **AC4**: Access 토큰(JWT)에는 **사용자 식별자와 만료 시간만** 포함된다. **역할 정보는 토큰에 넣지 않고** 서버가 매 요청 조회·판정한다(권한 변경 즉시 반영, FND-006·FND-010 참조).

### FND-004 토큰 검증·강제 차단
- 모든 보호된 API는 토큰을 검증한다. 만료·위조 토큰은 401을 반환한다.
- 매 보호 요청마다 서버가 **계정 활성 상태와 토큰 버전**을 확인한다. 비활성·퇴사·로그아웃·강제 만료된 토큰은 즉시 차단된다(만료를 기다리지 않음).
- 로그아웃·퇴사 시 Refresh 토큰을 폐기하고 토큰 버전을 올려 기존 Access 토큰을 무효화한다.
- **AC1**: 만료된 토큰으로 보호 API 호출 시 401.
- **AC2**: 서명이 위조된 토큰은 401.
- **AC3**: 로그인 세션 중 계정이 비활성화되면, 다음 요청부터 즉시 차단된다(401/403).
- **AC4**: 로그아웃 후 이전 Access·Refresh 토큰으로는 접근이 거부된다.

> 비밀번호 정책은 기본 수준(주기적 변경 강제·특수문자 필수 없음). **비밀번호 재설정은 시스템관리자 주도 리셋**(임시 비밀번호 발급 → 최초 로그인 시 변경 강제)으로 한다. 외부 이메일을 사용하지 않으므로(NOTI-001) 본인 셀프 재설정 링크는 제공하지 않는다. 계정 잠금 등 상세는 `10-nonfunctional.md`.

## 3. 권한 (RBAC)

### FND-005 역할 정의
5개 역할: `일반사용자`, `부서관리자`, `거점관리자`, `비품관리자`, `시스템관리자`.
- **AC1**: 한 사용자는 여러 역할을 동시에 가질 수 있다.
- **AC2**: 역할은 RBAC로 API 접근을 제어한다(권한 없는 호출은 403).

### FND-006 역할의 적용 범위(Scope)
- `부서관리자`·`거점관리자`는 **지정받은 범위**만 관리한다. 역할 부여는 `(역할, 적용대상 ID)` 쌍으로 저장.
  - 예: `홍길동 = 거점관리자 @LOC-서울`, `김철수 = 부서관리자 @DEPT-영업`.
- 소속 부서라고 해서 자동으로 부서관리자 권한이 생기지 않는다(담당/소속과 권한은 별개).
- `비품관리자`의 범위 부여 방식도 동일(담당 거점 범위 지정 가능).
- `시스템관리자`는 전역 권한.
- **AC1**: 부서관리자는 지정 범위 외 부서의 관리 API 호출 시 403.
- **AC2**: 거점관리자는 지정 범위 외 거점의 관리 API 호출 시 403.
- **AC3**: 범위는 다대다로 부여 가능하다(한 사람이 여러 부서/거점 관리 가능).
- 역할·범위 부여/회수는 **즉시 반영**된다(역할을 토큰에 고정하지 않고 매 요청 서버 조회 — FND-003 AC4).
- **AC4**: 역할을 회수하면 대상 사용자의 다음 요청부터 해당 관리 API가 403이 된다(재로그인 불요).

### FND-010 역할 기반 화면 접근 통제
- **단일 웹 앱** 내에서 역할에 따라 접근 가능한 화면(라우트)을 통제한다. 별도 관리자 앱/도메인으로 분리하지 않는다.
- 관리자 전용 화면군: 시스템 관리(임직원·조직·권한·서명키·공휴일), 범위 관리(부서/거점/비품 — FND-006 범위 내). 메뉴는 사용자의 역할에 해당하는 항목만 **동적으로 노출**한다.
- **프론트 라우트 가드는 UX·실수 방지용 보조 수단이며, 실제 권한 경계는 백엔드 API의 RBAC다**(NFR-SEC-004). CSR 구조상 관리자 페이지 코드가 클라이언트 번들에 포함되더라도 민감 데이터·동작은 API 권한 검사로만 통제된다.
- 같은 화면이라도 **조회와 편집(등록·수정·삭제) 권한을 분리**한다(예: 거점 현황은 전사 조회 가능(LOC-005)하되 편집은 해당 범위 관리자만).
- 다중 역할 보유 시 각 역할의 메뉴 항목이 함께 노출된다. 다중 범위 보유 시 목록 화면에서 자기 범위만 필터되어 표시·편집된다.
- **AC1**: 일반사용자가 관리자 전용 라우트에 직접 접근하면 화면이 노출되지 않는다(차단/리다이렉트).
- **AC2**: 범위 관리자는 부여된 범위(FND-006)의 관리 화면·액션만 사용 가능하며, 범위 밖 편집 API 호출은 403.
- **AC3**: 프론트 차단과 무관하게 관리자 전용 API는 백엔드 RBAC로 강제된다(권한 없는 호출 403).
- **AC4**: 조회 권한만 있는 사용자에게 편집 액션(버튼·API)이 차단된다(편집 API 호출 시 403).
- **AC5**: 다중 역할 사용자는 일반 업무 화면과 자신의 관리 화면을 한 앱에서 모두 사용할 수 있다(시스템관리자도 결재 상신 등 일반 업무 수행 가능).

## 4. 결재 서명 키 (전자결재 전용)

### FND-007 키 발급
- 시스템이 사용자별 RSA-2048 키쌍을 발급한다. **공개키만 DB에 저장**하고, 개인키는 발급 시 1회 파일 다운로드로 사용자에게 전달한다.
- **AC1**: 키 발급 후 서버에는 공개키만 존재하고 개인키는 저장되지 않는다.
- **AC2**: 개인키 다운로드 화면은 1회만 제공되며, "재발급 불가" 경고와 저장 확인 절차를 거친다.
- **AC3**: 공개키는 상태(활성/폐기)와 키 ID, 생성일시를 가진다.

### FND-008 서명·검증
- 결재 서명은 **브라우저(Web Crypto API)**에서 개인키로 수행한다. 개인키는 네트워크로 전송되지 않는다.
- 서버는 저장된 공개키로 서명을 검증한다. 검증 시 **서명에 기록된 공개키 ID**로 해당 키를 찾는다.
- **AC1**: 유효한 개인키로 만든 서명은 서버 검증을 통과한다.
- **AC2**: 위조 서명은 검증에 실패한다(결재 거부).
- **AC3**: 각 서명 레코드에는 사용된 공개키 ID가 함께 저장된다.

### FND-009 키 폐기·재발급
- 개인키 분실 시 시스템 관리자가 기존 공개키를 **폐기(비활성)**하고 새 키쌍을 재발급한다.
- 폐기된 공개키도 **삭제하지 않고 보존**한다(과거 서명 검증용).
- 재발급 이후의 서명에는 새 키가 적용되며, 이전 서명의 유효성에는 영향을 주지 않는다.
- **AC1**: 폐기 후에도 과거 서명은 폐기된 공개키로 검증 가능하다.
- **AC2**: 재발급 후 새 서명은 새 공개키로 검증된다(한 문서에 옛/새 키 서명 혼재 허용).
- **AC3**: 키 폐기·재발급은 감사 로그에 기록된다.

## 모듈화 가이드 (TDD)
- `auth` 패키지: 로그인·JWT 발급/검증. 순수 검증 로직(비밀번호 정책 등)은 프레임워크 비의존 함수로.
- `org` 패키지: 임직원·부서 CRUD, 조직 트리 규칙(3단계 제한)은 순수 함수로 분리해 단위 테스트.
- `signature` 패키지: 서명 검증을 도메인 서비스로 분리(공개키 조회 인터페이스를 주입받아 테스트 시 목 사용).
- RBAC 권한 판정은 `(사용자 역할들, 요청 대상 범위) → 허용/거부`의 순수 함수로 만들어 표 기반 테스트.
