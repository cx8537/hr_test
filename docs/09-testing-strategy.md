# 09. 테스트 전략 (TDD)

이 프로젝트는 **TDD(Red → Green → Refactor)**로 개발한다. 이 문서는 그것이 가능하도록 하는 모듈화 원칙과 테스트 매핑 규칙을 정의한다.

---

## 1. TDD 사이클 (필수 준수)
1. **Red**: 요구사항의 인수 기준(AC)을 테스트로 먼저 작성하고 실패를 확인한다.
2. **Green**: 그 테스트를 통과시키는 **최소** 구현을 한다.
3. **Refactor**: 중복 제거·구조 개선. 테스트는 계속 통과.
- 비즈니스 로직은 **테스트 없이 추가하지 않는다.**

## 2. 요구사항 → 테스트 매핑
- 모든 AC는 최소 1개 테스트로 매핑된다.
- 테스트 메서드명에 요구사항 ID를 포함한다.
  - 예: `AP012_병렬결재_1인반려시_즉시전체반려()`
  - 예: `AP042_휴가일수_주말과공휴일제외()`
- 커밋 메시지에도 관련 요구사항 ID를 명시한다.
- 추적성: 요구사항 문서의 AC ↔ 테스트가 1:N으로 연결되어야 하며, 누락 AC가 없어야 한다.

## 3. 테스트 피라미드
- **단위 테스트(다수)**: 순수 도메인 로직. 빠르고 격리됨. 대부분의 비즈니스 규칙은 여기서 검증.
- **통합 테스트(중간)**: Repository·DB·MinIO·트랜잭션·동시성. 실제 PostgreSQL 사용(테스트용 로컬 인스턴스 또는 Testcontainers 대체로 로컬 임베디드 옵션 — Docker 미사용 환경이므로 로컬 PostgreSQL 테스트 스키마 사용).
- **E2E/시나리오(소수)**: 핵심 흐름(상신→결재완료→자동보관, 예약 중복 차단 등) 위주. **시스템 가동 후 역할별 브라우저 인수 검증은 `13-e2e-acceptance.md`** 에 별도 명세(Playwright MCP 탐색 + 코드 회귀).

## 4. 모듈화 원칙 (테스트 용이성의 핵심)
**비즈니스 규칙을 프레임워크에서 분리한다.** 다음은 모두 순수 함수/도메인 서비스로 분리하여 DB 없이 단위 테스트한다.

| 도메인 로직 | 입력 → 출력 | 요구사항 |
|------------|------------|---------|
| 결재 흐름 엔진 | (결재선 스냅샷, 진행상태, 액션) → 다음 상태 | AP-010~013, 030~033 |
| 전결 결재선 생성기 | (기본 결재선, 전결 단계) → 잘린 결재선 | AP-020 |
| 휴가 일수 계산기 | (시작일, 종료일, 반차, 공휴일목록) → 일수 | AP-042 |
| 지출 합계 계산 | (행 목록) → 합계 | AP-041 |
| 수량 산출 | (입출고 이력) → 현재 수량 | AST-003 |
| 예약 시간 겹침 판정 | (기존 예약들, 신규 시간대) → 겹침 여부 | RSV-003 |
| RBAC 권한 판정 | (사용자 역할들, 대상 범위) → 허용/거부 | FND-006 |
| 문서 공개범위 판정 | (공개범위, 요청자, 관여자) → 허용/거부 | DOC-005 |
| 서명 검증 | (데이터, 서명, 공개키) → 유효성 | FND-008 |
| 비활성화 가능 판정 | (소속 존재 여부) → 허용/거부 | LIFE-B/C |

> 이 표의 각 행은 독립적으로 테스트 가능한 단위다. Controller·Repository는 이 순수 로직을 호출·조립하는 얇은 층으로 유지한다.

## 5. 계층 구조
```
Controller (HTTP, 얇음)
  → Service (도메인 로직 조립, 트랜잭션 경계)
    → Domain (순수 규칙: 위 표) ← 단위 테스트 집중
    → Repository (영속성) ← 통합 테스트
```
- 도메인 계층은 Spring 비의존(POJO). 외부 의존(공개키 조회, 시계, 공휴일 조회)은 인터페이스로 주입 → 테스트 시 목/스텁 사용.
- 시간 의존 로직(휴가 일수, 미래 예약 판정)은 `Clock`을 주입해 결정론적 테스트. 운영·테스트 모두 **타임존은 KST 고정**(`10`·`12`).

## 5-1. 자원별 동시성 전략
동시성은 자원 성격에 따라 전략이 다르다. 통합 테스트로 검증한다.

| 자원 | 전략 | 요구사항 |
|------|------|---------|
| 예약 시간 겹침 | DB **EXCLUSION 제약**(GiST+tstzrange) | RSV-003 |
| 결재 상태 전이 | **비관적 락**(SELECT FOR UPDATE) + 상태 재검증 | AP-033 |
| 일반 편집(거점·비품·자원) | **낙관적 잠금**(version 컬럼) | NFR-PERF-003 |
| 비품 수량 입출고 | 트랜잭션 일관성(음수 방지) | AST-003 |
| 인증·권한 | 매 요청 계정상태·토큰버전 검증 | FND-004 |

> 동시성 AC(동시 예약 한 건만, 동시 승인·회수 일관성, 동시 편집 충돌 거부)는 통합 테스트로 반드시 포함한다.

## 6. 모듈(패키지) 경계
독립 패키지로 분리하고 모듈 간은 인터페이스/이벤트로 결합 최소화:
`auth`, `org`, `signature`, `approval`, `location`, `asset`, `reservation`, `document`, `notification`.
- 모듈 간 부수효과(결재완료 → 문서 자동보관, 예약취소 → 알림)는 **도메인 이벤트**로 처리. 발행/구독을 분리해 각 측을 독립 테스트.

## 7. 커버리지·품질 기준
- 도메인 계층(위 표): 분기 커버리지 높게 유지(경계값·예외 경로 포함).
- 모든 "거부/실패" AC(예: 중복 거부, 권한 403, 음수 수량 거부)는 **부정 테스트**를 반드시 포함.
- 테스트는 결정론적이어야 한다(랜덤·실시간 시계 직접 사용 금지 → 주입).

## 8. 권장 테스트 도구
- 백엔드: JUnit 5, AssertJ, Mockito. 통합은 Spring Boot Test + 로컬 PostgreSQL 테스트 스키마.
- 프론트: 컴포넌트/로직 단위 테스트(예: Vitest/Jest + Testing Library). 폼 분기(차량/회의실), 일수 표시 등.
- 서명 검증은 백엔드·프론트 양쪽에서 동일 알고리즘(RSA-2048) 호환성 테스트.
